# 開発優先度ロードマップ

## 評価軸の定義

| 軸 | 説明 | スケール |
|----|------|---------|
| **開発メリット** | ユーザー・プロダクトへの価値。セキュリティ・分析・UX・品質・再現性で評価 | 1〜5（5=最高） |
| **開発工数** | ファイル数・新規ツール学習・CI変更・設定量の合計 | 1〜5（1=最小） |
| **ROI スコア** | メリット ÷ 工数。高いほど「少ない工数で大きな価値が出る」 | 高いほど先着手すべき |

## ブロック関係図

```
[CF Pages 移行 + Auth]
        │
        ├──(必須)──→ [Terraform IaC]
        │              CF Pages プロジェクトが存在しないと
        │              Terraform で管理するリソースが定義できない
        │
        └──(推奨)──→ [GA4 タグ]
                       技術的には GitHub Pages でも動くが、
                       Cloudflare Pages の環境変数機能を使うと
                       prod/staging の切り替えが格段に楽になる

[カスタム Svelte コンポーネント]
        │
        └──(推奨)──→ [URL パラメータフィルター]
                       フィルター UI の実装パターン（ドロップダウン等）が
                       コンポーネントと共通のため、先に作っておくと流用できる

[DuckDB 移行]           → 独立。どの項目とも依存なし
[E2E Playwright]        → 独立。ただし機能が安定してから着手すると費用対効果が高い
```

### ブロック関係の種別

| 種別 | 説明 |
|------|------|
| **必須ブロック** | 前のタスクが完了しないと技術的に着手できない |
| **推奨ブロック** | 独立して着手できるが、前のタスクを終えてからの方が効率・品質が上がる |

## 推奨着手順序

ROI・ブロック関係・学習効果を総合した推奨順序は以下のとおり。

```
フェーズ 1（セキュリティ基盤）
  └─ CF Pages 移行 + Access 認証
       理由: 現状は URL を知れば誰でも閲覧可能。
             他のすべての改修の土台になるホスティング環境を先に固める。
             コード変更なし・設定作業メインで工数が少ない。

フェーズ 2（計測・可視性）
  └─ GA4 タグ埋め込み
       理由: 工数 1（1ファイル作成 + 環境変数設定）で ROI 最大。
             CF Pages 移行後なら環境変数管理が整っており最もスムーズ。
             誰がどのページを見ているかの計測が早期に始まるほど蓄積データが増える。

フェーズ 3（ダッシュボード品質）
  └─ カスタム Svelte コンポーネント
       理由: データソースに依存せず現在の CSV のまま実装可能。
             KpiCard / TrendBadge / StatusBar の 3 ファイルで完結し工数が読みやすい。
             次の URL パラメータフィルターで UI コンポーネントを流用できる。

  └─ DuckDB 移行・複数テーブル（カスタムコンポーネントと並行可）
       理由: コンポーネント実装と独立しているため並行作業が可能。
             正規化されたテーブル構成を先に整えると、
             以降の分析ページ追加がシンプルになる。

フェーズ 4（ユーザビリティ）
  └─ URL パラメータフィルター
       理由: カスタムコンポーネントと DuckDB が揃ったタイミングで実装すると、
             リッチなデータをフィルターで絞り込む体験として完成度が高くなる。

フェーズ 5（品質保証 / 再現性）
  └─ E2E テスト（Playwright）
       理由: フェーズ 1〜4 で機能が安定してから導入すると
             テストが壊れにくくなり維持コストが下がる。

  └─ Terraform IaC
       理由: CF Pages が稼働してから整備。
             学習コストが最も高く、他の改修に影響しない独立した作業のため最後でよい。
```

## 項目別メリット詳細

### CF Pages 移行 + Access 認証（メリット: 5）
- 現状は URL 知得者全員が閲覧可能という**セキュリティリスク**が存在する
- 改修後は許可されたメンバーのみがアクセス可能になる
- Cloudflare Pages のプレビュー URL 機能（PR ごとのステージング）が使えるようになる

### GA4 タグ埋め込み（メリット: 4）
- ダッシュボードの実際の利用状況（誰が・何を・どの順で見ているか）が把握できる
- カスタムディメンション（env / promotion_id）でフィルタリングした分析が可能
- 着手が遅いほど蓄積データが少なくなるため**早期実施で恩恵が大きい**

### DuckDB 移行・複数テーブル（メリット: 4）
- JOIN クエリが書けるようになり分析の幅が広がる
- データ正規化により CSV の重複・不整合を解消できる
- CI でデータを自動再構築できるようになるため、データ更新時の手作業が減る

### カスタム Svelte コンポーネント（メリット: 3）
- KPI・トレンド・目標達成率が一目でわかるようになり、閲覧者の認知コストが下がる
- 汎用コンポーネントとして他ページでも再利用できる

### URL パラメータフィルター（メリット: 3）
- フィルターの状態を URL で共有できるようになる
- リロードしてもフィルターが維持されるため作業効率が上がる

### E2E テスト（Playwright）（メリット: 3）
- グラフ描画・フィルター動作の自動検証により、デプロイ後のリグレッションを防げる
- CI に組み込むことで「動いているように見えてグラフが空」というサイレント障害を検知できる

### Terraform IaC（メリット: 2）
- インフラ設定をコードで再現できるようになる
- チームが増えたとき・環境を複製するときに効果を発揮するが、**現状の規模では恩恵が限定的**
